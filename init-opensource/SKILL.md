# Initialize Open-Source Repository

A skill for transforming a personal project into a publishable open-source repository. It generates all necessary documentation and configuration files using battle-tested templates. The user chooses which steps to run and which languages to support up front.

## Philosophy

- **Templates over improvisation**: For files that don't depend heavily on project-specific content (LICENSE, CODE_OF_CONDUCT, CONTRIBUTING), use the bundled templates exactly as-is. Do not rewrite or rephrase them.
- **User chooses scope first**: Ask the user which files they want and which languages they need before generating anything. Do not assume they want every file.
- **Smart defaults, user confirmation**: Auto-detect what we can (badges, .gitignore tech stack, author name), then present findings for confirmation.
- **English-first translation**: All non-English versions are translated from the English template, never from another language.

## Workflow Overview

Execute the following phases in order. Only run generation steps the user explicitly selected.

```
Phase 0: Select initialization steps (multi-select)
Phase 1: Select additional languages
Phase 2: If Issue/PR templates + non-English, select template language
Phase 3+: Execute selected generation steps
```

---

## Phase 0: Select Initialization Steps

Present the user with a multi-select question:

> "Which files would you like me to generate? Select all that apply."

**Options:**
- Git repository + .gitignore
- LICENSE
- CODE_OF_CONDUCT.md
- CONTRIBUTING.md
- Issue / PR templates
- README.md

Store the user's selections. Only run the corresponding steps below.

**If the user selected nothing**, confirm: "You didn't select any files. Should I skip initialization?"

---

## Phase 1: Select Additional Languages

Ask:

> "Besides English, do you need any other language versions?"

**Options:**
- No, English only
- Simplified Chinese (简体中文)
- Other language (please specify)

If the user selects "Other language", follow up with: "Which language do you need? (e.g., Japanese, French, Spanish)" and record their answer as the language code/request.

**Important:** All non-English versions are generated by translating the **English** template. Never translate from Chinese or any other intermediate language.

---

## Phase 2: Issue / PR Template Language (Conditional)

Only execute this phase if **both**:
- "Issue / PR templates" was selected in Phase 0
- A non-English language was selected in Phase 1

Ask:

> "Should the Issue and Pull Request templates use the non-English language, or stay in English?"

**Options:**
- Keep Issue/PR templates in English
- Use [selected language] for Issue/PR templates

Record the choice for Step 5.

## Step 1: Initialize Git Repository + .gitignore

**Skip this step if "Git repository + .gitignore" was not selected in Phase 0.**

### Check
- Is there already a `.git` directory in the project root?
- Does `.gitignore` already exist?

### Ask user
"I can initialize a Git repository and generate a `.gitignore` based on your tech stack. Should I proceed?"

### Auto-detect tech stack for .gitignore
Look at the project files to infer what technologies are used:

| File/Directory | Technology | gitignore.io Keyword |
|---|---|---|
| `package.json` | Node.js | `node` |
| `Cargo.toml` | Rust | `rust` |
| `go.mod` | Go | `go` |
| `requirements.txt`, `pyproject.toml`, `setup.py` | Python | `python` |
| `pom.xml`, `build.gradle` | Java | `java` |
| `Gemfile` | Ruby | `ruby` |
| `composer.json` | PHP | `composer` |
| `*.swift`, `Package.swift` | Swift | `swift` |
| `*.kt`, `*.kts`, `build.gradle.kts` | Kotlin | `kotlin` |
| `Dockerfile`, `docker-compose.yml` | Docker | `docker` |

If multiple technologies are detected, combine them.

**Note on keywords:** gitignore.io accepts technology names as lowercase keywords. The full list of supported keywords can be viewed with:
```bash
curl -sL https://www.toptal.com/developers/gitignore/api/list
```
If an invalid keyword is sent, the API may return an empty or minimal file. In that case, use the fallback method below.

### Generate .gitignore
**Preferred method** — use gitignore.io API if Bash is available:

```bash
curl -sL "https://www.toptal.com/developers/gitignore/api/{tech1},{tech2},macos,windows,linux" > .gitignore
```

Always include `macos,windows,linux` for OS-specific files.

**Fallback method** — if Bash/curl is unavailable or the API returns insufficient content, use Write to create the file with these common patterns:

- **Node.js**: `node_modules/`, `npm-debug.log*`, `dist/`, `build/`, `.env`
- **Python**: `__pycache__/`, `*.py[cod]`, `.venv/`, `env/`, `dist/`, `build/`, `*.egg-info/`
- **Rust**: `target/`, `Cargo.lock`
- **Go**: `bin/`, `vendor/`
- **Java**: `*.class`, `target/`, `.gradle/`, `build/`
- **OS files**: `.DS_Store`, `Thumbs.db`, `desktop.ini`

Combine all detected tech stacks into a single `.gitignore` file.

## Step 2: Generate LICENSE

**Skip this step if "LICENSE" was not selected in Phase 0.**

### Check
- Does `LICENSE` or `LICENSE.txt` or `LICENSE.md` already exist?

### Ask user
"I can generate an open-source license. Which license would you like?"

**Options:**
- MIT (recommended — most permissive, most popular, simplest)
- Apache-2.0 (patent protection, enterprise-friendly)
- GPL-3.0 (copyleft, derivatives must be open-source)
- LGPL-3.0 (copyleft for libraries, linking allowed)
- BSD-3-Clause (permissive, academic)
- MPL-2.0 (file-level copyleft, Mozilla-style)
- ISC (simple, permissive, MIT-like)
- CC0-1.0 (public domain dedication, no copyright)
- Unlicense (public domain dedication)
- Skip

If the user is unsure, recommend MIT: "If you're not sure, MIT is the safest default — it's the most widely used open-source license and places almost no restrictions on users."

### Generate
Copy the corresponding template file and replace placeholders:

```bash
cp templates/license/{key}.md LICENSE
sed -i 's/\[year\]/{CURRENT_YEAR}/g; s/\[fullname\]/{AUTHOR_NAME}/g' LICENSE
```

Or if using Write: read the template once with `Bash cat`, then Write the modified content to `LICENSE`.

Replace:
- `[year]` → current year
- `[fullname]` → user's name

**Author name detection:**
1. Try `git config user.name`
2. If empty/unset, ask the user: "What name should appear as the copyright holder?"

## Step 3: Generate CODE_OF_CONDUCT.md

**Skip this step if "CODE_OF_CONDUCT.md" was not selected in Phase 0.**

### Check
- Does `CODE_OF_CONDUCT.md` already exist?

### Ask user
"I can generate a Code of Conduct based on the Contributor Covenant (v2.1). Should I proceed?"

### Generate
Copy the template and replace the contact placeholder:

```bash
cp templates/coc/{en|zh}.md CODE_OF_CONDUCT.md
sed -i 's/\[INSERT CONTACT_METHOD\]/{contact_method}/g' CODE_OF_CONDUCT.md
```

Or use Write after reading with `Bash cat`.

Replace `[INSERT_CONTACT_METHOD]` with the contact email or method the user provides.

**Contact method:**
1. Try `git config user.email`
2. Present to user: "I'll use [email] as the contact for conduct violations. Is that correct?"
3. **Options:** Yes, use this / No, I'll enter a different one / Skip (leave placeholder)
4. If "No, I'll enter a different one", ask: "What contact method should people use? (e.g., email@example.com)"

---

## Step 4: Generate CONTRIBUTING.md

**Skip this step if "CONTRIBUTING.md" was not selected in Phase 0.**

### Check
- Does `CONTRIBUTING.md` already exist?

### Ask user
"I can generate a comprehensive contributing guide. Should I proceed?"

### Generate
Copy the template and replace placeholders:

```bash
cp templates/contributing/standard.md CONTRIBUTING.md
sed -i 's/\[Project Name\]/{project_name}/g; s/\[Default Branch\]/{default_branch}/g; s/\[Repository URL\]/{repo_url}/g; s/\[Documentation URL\]/{docs_url}/g; s/\[Security Email\]/{security_email}/g' CONTRIBUTING.md
```

Or use Write after reading with `Bash cat`.

**Placeholder resolution:**

| Placeholder | Detection Strategy | If Undetectable |
|---|---|---|
| `[Project Name]` | `package.json` → `name`, `Cargo.toml` → `package.name`, directory name | Ask: "What is the project name?" |
| `[Default Branch]` | `git branch --show-current` | Ask: "What is the default branch? (common: main, master)" |
| `[Repository URL]` | `git remote get-url origin` | Ask: "What is the full repository URL?" |
| `[Documentation URL]` | Same as repo URL, or ask | Ask: "Is there a separate documentation URL? (press Enter to use repo URL)" |
| `[Security Email]` | `git config user.email` | Ask: "What email should be used for security reports?" |

For each value, first try auto-detection. Present the detected value to the user for confirmation:
> "I detected [value] for [placeholder]. Is this correct?"

**Options:** Yes / No, I'll enter a different value / Skip this placeholder

If "No, I'll enter a different value", ask the specific question in a follow-up.

## Step 5: Generate Issue / PR Templates

**Skip this step if "Issue / PR templates" was not selected in Phase 0.**

### Check
- Does `.github/ISSUE_TEMPLATE/` already exist with templates?
- Does `.github/PULL_REQUEST_TEMPLATE.md` already exist?

### Ask user
"I can generate GitHub issue templates (bug report, feature request) and a pull request template. Should I proceed?"

### Generate
Create `.github/ISSUE_TEMPLATE/` directory and copy templates.

**Language selection:**
- If Phase 2 was reached and the user chose to use the non-English language, use `{lang}` templates
- Otherwise, use English templates

```bash
mkdir -p .github/ISSUE_TEMPLATE
cp templates/issue-pr/bug_report{.{lang}}.md .github/ISSUE_TEMPLATE/
cp templates/issue-pr/feature_request{.{lang}}.md .github/ISSUE_TEMPLATE/
cp templates/issue-pr/pull_request_template{.{lang}}.md .github/PULL_REQUEST_TEMPLATE.md
```

For `config.yml`, write a new file (it has `{OWNER}` and `{REPO}` placeholders):

```yaml
blank_issues_enabled: false
contact_links:
  - name: Questions & Discussions
    url: https://github.com/{OWNER}/{REPO}/discussions
    about: Please ask and answer questions here.
```

## Step 6: Generate README.md

**Skip this step if "README.md" was not selected in Phase 0.**

### Check
- Does `README.md` already exist?
- If yes, evaluate its completeness (does it have: title, description, installation, usage, badges, contributing link, license link?)

### Ask user
If README exists: "You already have a README. Should I enhance it with a better structure, badges, and cross-references?"
If no README: "I can generate a professional README with badges, feature list, and links to all generated docs. Should I proceed?"

### Generate approach
Use the README template from `templates/readme/template.md` as the structural foundation, then populate it based on project analysis.

**Template structure** (do not deviate from this order):
1. Project title (h1)
2. Optional banner placeholder (commented)
3. Language switcher links
4. Badges row
5. Project description (blockquote)
6. Features list
7. Installation section
8. Quick start section
9. Documentation link
10. Contributing link
11. License link
12. Optional acknowledgments

### Project analysis for README content
Analyze the project to fill in:

- **Project name**: From `package.json` → `name`, `Cargo.toml` → `package.name`, directory name, or ask
- **Description**: From `package.json` → `description`, `Cargo.toml` → `package.description`, or ask
- **Install command**: Infer from package manager:
  - npm/yarn/pnpm → `npm install {package-name}`
  - cargo → `cargo add {package-name}`
  - pip → `pip install {package-name}`
  - go → `go get {module-path}`
- **Quick start**: Look for a main entry point, CLI usage, or basic API example. Extract a minimal example if possible.

### Badges
Auto-detect which badges are relevant and present them to the user for confirmation.

**Detection logic:**

| Badge Type | Detection Method |
|---|---|
| npm version | `package.json` exists |
| npm downloads | `package.json` exists + ask package name |
| crates.io | `Cargo.toml` exists |
| PyPI | `pyproject.toml` or `setup.py` exists |
| Go Reference | `go.mod` exists |
| Build Status | Ask if CI is set up |
| Coverage | Ask if codecov/coveralls is used |
| License | From Step 2 selection (if selected) |
| Stars | Ask GitHub repo URL |

For each detected badge, show the user:
"I detected you might want these badges: [list]. Should I include them? You can also add custom ones."

**Options:** Include all / Let me pick which ones / Skip badges

If "Let me pick which ones", present each badge as a checkbox option.

Common badge markdown patterns:
```markdown
![npm](https://img.shields.io/npm/v/{package-name})
![npm downloads](https://img.shields.io/npm/dm/{package-name})
![License](https://img.shields.io/github/license/{owner}/{repo})
![Stars](https://img.shields.io/github/stars/{owner}/{repo})
![Build Status](https://img.shields.io/github/actions/workflow/status/{owner}/{repo}/{workflow-file})
```

Use shields.io for all badges.

## Multi-Language File Generation

After all selected generation steps are complete, if a non-English language was selected in Phase 1, generate translated versions for each file that supports it.

For each document that has a language variant in `templates/`:
1. Generate the non-English version by translating the English template
2. Save as `{filename}.{lang}.md` (e.g., `README.zh.md`)
3. Add language switcher links at the top of BOTH versions

**Language switcher format** (at the very top of the file, after any banner):
```markdown
<p align="center">
  <a href="./README.md">English</a>
  ·
  <a href="./README.zh.md">简体中文</a>
  ·
  <a href="./README.ja.md">日本語</a>
</p>
```

**Supported language mappings from templates:**
- `zh` → 简体中文

For languages not in the template set, translate from the English template using Claude's translation capability. Do not translate from Chinese.

## Template Sources and Updates

All bundled templates were downloaded from authoritative sources:

| Template | Source | URL |
|---|---|---|
| LICENSE (all variants) | GitHub choosealicense.com | `https://raw.githubusercontent.com/github/choosealicense.com/gh-pages/_licenses/{key}.txt` |
| CODE_OF_CONDUCT | Contributor Covenant v2.1 | `https://www.contributor-covenant.org/version/2/1/code_of_conduct/code_of_conduct.md` |
| CONTRIBUTING | contributing.md example template | `https://contributing.md/example/` |
| Issue/PR Templates | GitHub official templates | `https://github.com/github/docs` |
| .gitignore | gitignore.io (Toptal) | `https://www.toptal.com/developers/gitignore/api/{tech}` |

To update templates, run the update script (see `scripts/update-templates.sh`) which re-downloads all templates from their sources.

## Important Notes

- **Do not rewrite templates**: For LICENSE, CODE_OF_CONDUCT, and CONTRIBUTING, use the bundled templates verbatim. Only replace the specific placeholders documented above.
- **README is the exception**: The README template provides structure, but content should be filled based on actual project analysis.
- **Always check first**: Before creating any file, check if it exists and assess its quality. Don't overwrite good content without asking.
- **Every step is optional by design**: The user explicitly selects which steps to run in Phase 0. Respect that selection.
- **Input guidance pattern**: When a value is needed, offer "Use default / Skip / Enter custom value" as options. Never put an input prompt inside an option label. Collect custom values in a follow-up question.
